## 1. 지금까지의 진행 (2026-08-11 기준)

### 왜 이 시험을 하나

VICA 음성 파이프라인의 LLM(gemma4:cloud, Ollama)을 gpt-realtime-2.1-mini 로
바꾸는 것을 검토 중이다. 동기 세 가지:

| 문제 | 현재 | 근거 |
| --- | --- | --- |
| LLM 왕복 지연 | ~3.5초 | `docs/jetson-handoff.md:116` |
| 지연을 가리는 임시방편 | "네." 선응답 | `ros_node.py` (LLM 대기 중 침묵 방지) |
| Jetson GPU 경합 | nvblox ↔ whisper | 워크스페이스 devlog 2026-07-30 실측 |

### 검토 보고서의 결론 (요약)

1. LLM 결합 지점은 `src/langchain_intent_parser.py` 한 파일 15줄뿐 — 교체 자체는 쉽다
2. **Realtime API 에는 Structured Output 이 없다.** 구조화 채널은 function calling 뿐
3. 그래서 도입 형태는 "FC 를 SO 처럼 묶어 쓰기": **단일 도구 `report_intent`
   (스키마 = 기존 `_IntentDraft`) + `tool_choice` 강제 + 출력은 텍스트만**
4. 음성 **출력**(로봇 목소리)까지 모델에 맡기는 것은 금지 — 긴급어 선차단·
   `/vica/tts_state` 자가 트리거 방지·TTS 우선순위 선점과 정면 충돌
5. 긴급어 경로(모델 B + 로컬 whisper)는 어떤 경우에도 온디바이스 불변
6. **도입 확정은 감이 아니라 실측 후에 한다** ← 이 시험이 그 실측이다

모델 사양 (2026-08 조사): 2026-07-07 출시, 오디오 토큰 입력 $10/출력 $20 per 1M
(분당 약 $0.016), function calling·reasoning 지원, WebSocket/WebRTC/SIP.

### 이 시험이 답할 질문 — 판단 축 4종

측정이 끝나면 아래 네 축을 7절의 숫자를 인용해 판단한다. "더 좋아 보인다"는
결론이 아니다.

| 축 | 비교 | 근거 숫자 |
| --- | --- | --- |
| 지연 | A 기준선 vs B realtime | 3-4 단계별·전체 중앙값 |
| 연산량 | 변형별 온디바이스 부하 | 3-5 tegrastats 기록 |
| LLM 위치 | 로컬 vs 클라우드 | 지연 + 연산량 + 연결 안정성 종합 |
| 구조화 채널 | SO vs FC | 3-2 준수율 (A 는 SO, B 는 FC) |

주의 두 가지:

- 현행 LLM(gemma4:cloud)은 **이미 클라우드**다. "로컬이 좋은가"에 제대로 답하려면
  같은 하네스로 로컬 모델(예: Ollama 로컬 gemma) 변형 C 를 한 번 더 돌려야 한다.
  시간이 없으면 C 는 후속 시험으로 미루고 그 사실을 7절에 적는다.
- Realtime API 에는 SO 가 없다(위 결론 2). 따라서 SO vs FC 는 "현행 REST 경로의
  SO(`with_structured_output`) 실패율 vs realtime FC 실패율"의 비교다.

## 2. 준비

```bash
cd <workspace>/vica-voice-llm
git fetch origin && git checkout test/gpt-realtime-2026-08-11
source .venv/bin/activate
pip install websockets        # venv 안에만. requirements.txt 에 추가 금지
```

`.env` 에 `OPENAI_API_KEY` 가 필요하다. **사용자에게 키를 요청해라** — 네가 만들 수
없다. 받으면 `.env` 에 한 줄 추가한다 (`.gitignore` 에 이미 있어 커밋되지 않지만,
그래도 `git status` 로 확인해라).

ROS·로봇 노드는 **필요 없다.** 단, 전 구간(STT→LLM→TTS)을 재므로 **마이크
(reSpeaker)와 스피커는 필요하다.** 이 젯슨에는 주행 스택(can1·safety·nvblox)이
없으므로 여기서 얻는 연산량은 경합 없는 **단독 수치**다 — 7절에 그렇게 명기한다.

연산량은 `tegrastats`(`/usr/bin/tegrastats`, 이 젯슨에 있음)로 잰다:

```bash
tegrastats --interval 500 --logfile logs/tegrastats_<변형>_<회차>.log
# 측정 블록 시작 직전에 켜고, 끝나면 tegrastats --stop (또는 Ctrl-C)
```

## 3. 시험 절차 — 기준선 + 측정 5종

변형은 같은 발화 세트(3-3)로 같은 횟수, 같은 네트워크·시간대에 연달아 잰다:

- **A (기준선)**: 현행 whisper STT → gemma(Ollama Cloud, SO) → 로컬 TTS
- **B (후보)**: gpt-realtime-2.1-mini (음성→intent 한 왕복, FC) → 로컬 TTS
- C (선택): 로컬 LLM 변형 — 1절 판단 축 참고

**어느 변형이든 로봇 목소리는 기존 로컬 TTS 다.** 모델 audio 출력은 금지(4절).

### 3-0. 기준선 — 현행 파이프라인 전 구간 실측 (필수)

`src/main.py` 에는 시간 계측이 없다(`SpanTracker` 는 ROS 시뮬 로그 전용).
계측은 전용 하네스 `scripts/pipeline_probe.py` 로 한다 (작성됨·[미검증].
사용법은 그 파일 머리 주석에 있다):

- src/ 모듈(VicaSTT·parse_intent·VicaTTS)을 **import 만** 하고 수정하지 않는다
- 단계 경계마다 `time.perf_counter()`: 발화 종료→STT 텍스트→intent→TTS 재생 시작
- **TTS 재생 종료는 버튼 실측이 1차 수치다.** 스크립트가 "재생이 끝나는 순간
  Enter" 를 안내하고 keypress 시각을 기록한다. 스피커에서 소리가 실제로 끝나는
  순간은 사람 귀가 가장 정확하다 — 프로세스 타임스탬프는 오디오 버퍼 잔량을
  놓친다. 기계 쪽 타임스탬프(`tts.speak` 반환 시각)도 참조용으로 병기하고,
  사람 반응 오차(~±0.2초)는 반복 중앙값으로 흡수한다
- SO 실패(파싱 예외·필드 누락)도 회차마다 센다 — SO vs FC 판단 자료(1절)다
- 회차마다 jsonl 한 줄: 시작·종료 시각, 단계별 sec, 발화, intent, 판정
- 같은 버튼 프로토콜을 B(탐침 응답을 로컬 TTS 로 재생)에도 그대로 쓴다

기록: 발화 세트 6종 × 10회(텍스트 입력) / 6종 × 5회 이상(음성 입력)의
단계별·전체 중앙값

### 3-1. 연결이 되는가 (스크립트 디버깅 포함)

```bash
.venv/bin/python scripts/gpt_realtime_probe.py --text "화장실로 가줘"
```

스크립트는 GA(2025-08+) 이벤트 형식으로 작성됐고 **실행된 적이 없다.** `[오류]` 가
출력되면 그 JSON 이 디버깅의 출발점이다. 스크립트의 `_session_update()` 주석에
구형(beta) 키 대응표를 적어 뒀다. 고쳐서 돌게 만들고, **무엇을 고쳤는지 이 문서
7절에 기록해라.**

기록: WebSocket open 시간, session.updated 까지 시간 (세션 수명 정책 결정의 근거다)

### 3-2. 스키마 준수 — tool_choice 강제가 실제로 동작하는가

같은 명령을 **10회** 반복하고 스크립트 출력의 `[스키마]` 줄을 센다.

| 확인 | 통과 기준 |
| --- | --- |
| function_call 없이 끝난 횟수 (`[경고]` 줄) | 0 / 10 |
| 필수 필드(intent, reply) 누락 | 0 / 10 |
| intent 가 enum 밖의 값 | 0 / 10 |

하나라도 실패하면 **strict 스키마의 Realtime 지원이 불완전하다는 뜻**이고, 도입
시 재시도·검증 층이 추가로 필요해진다. 실패 사례의 JSON 을 그대로 기록해라.

### 3-3. 한국어 이해 — 발화 세트

텍스트로 먼저, 그다음 음성으로 같은 세트를 넣는다.

```bash
# 음성 샘플 녹음 (reSpeaker, 16k mono)
arecord -r 16000 -f S16_LE -c 1 -d 3 sample.wav
.venv/bin/python scripts/gpt_realtime_probe.py --wav sample.wav
```

| # | 발화 | 기대 intent | 기대 destination |
| --- | --- | --- | --- |
| 1 | "화장실로 가줘" | navigate | 화장실 |
| 2 | "배가 아파요" | navigate (간접) | 화장실 |
| 3 | "여기 몇 층이야?" | question | null |
| 4 | "저기로 가줘" | clarify | null |
| 5 | "취소해줘" | cancel | null |
| 6 | "밥 먹을 데 있어?" | navigate 또는 question | 식당 (판정 기록) |

현행과의 비교가 이 시험의 목적이므로, 같은 세트를 A(3-0 하네스)와 B(탐침)에
**모두** 넣어 나란히 기록한다. 선택이 아니라 필수다.

### 3-4. 지연 — 도입 판단의 핵심 숫자

A 는 3-0 하네스가, B 는 탐침이 출력한다. 10회 반복해 중앙값을 적는다.
전체 지연의 끝점은 **버튼으로 잰 TTS 재생 종료**다(3-0 프로토콜).

| 구간 | A 기준선 | B realtime |
| --- | --- | --- |
| 발화 종료 → 텍스트/intent | listen_stt_sec + llm_sec (참고: llm_sec ~3.5초) | 한 왕복으로 합산 |
| intent → TTS 재생 시작 | 측정 | 측정 |
| TTS 재생 (시작 → 종료[버튼]) | 측정 | 측정 |
| **전체 (발화 종료 → TTS 종료[버튼])** | 측정 | 측정 |

`[토큰]` 줄의 usage 도 함께 적어라 — 비용 개산(보고서 6절, 월 ~$24)의 검증 자료다.

### 3-5. 연산량 — 온디바이스 부하 비교

- 각 측정 블록 동안 tegrastats 를 500ms 간격으로 로깅한다(2절 명령)
- 하네스 jsonl 의 회차 시작·종료 시각으로 tegrastats 로그를 구간 절단한다
- 기록: 변형별 CPU%·RAM·GR3D(GPU)% 의 평균과 피크. **B 에서 whisper 가 빠진
  만큼 GPU 부하가 실제로 얼마나 줄었는가**가 핵심 숫자다
- 클라우드 쪽 연산량은 잴 수 없다 — 대신 usage 토큰과 비용으로 환산해 적는다
- 이 젯슨은 주행 스택이 없어 **경합 없는 단독 수치**임을 결과에 병기한다(2절)

## 4. 하지 말 것

- **`dev` 에 커밋·push 금지.** 결과는 이 브랜치에만
- **파이프라인 코드(src/) 수정 금지.** 계측은 `scripts/` 의 신규 하네스에서
  src/ 를 import 해서만 한다. 통합은 별도 단계다
- **`requirements.txt` 수정 금지.** websockets 는 venv 에만 설치한다
- **API 키를 코드·문서·커밋에 남기지 마라**
- **긴급어 경로(웨이크워드·emergency_filter)를 건드리지 마라** — 이 시험과 무관하고, 안전 계약이다
- 모델의 음성 출력(audio modality) 실험은 하지 마라 — 검토 보고서에서 금지로 결론난 축이다
