## 4. 원인 분석

- **(A) 미션의 질문이 LLM 이력에 없다.** LLM 노드 이력은 자기 reply 만 넣는다
  (`_history.extend([Human, AI(intent.reply)])`). "몇 분쯤 걸리실까요?"·"여기서 대기할까요?"는
  미션 매니저가 TTS 로 말하므로 두 경로 모두 '오 분'이 무슨 답인지 모른다(#7 양쪽 실패).
  `/vica/tts_done` 텍스트는 이미 받고 있다(echo 판정용) — 이력에도 넣으면 양쪽 다 이득.
- **(B) #11·#12 의 두 가지 해석.** 상황: 17:09:07 호출 → 로봇 인사 "…안내를 받으시겠어요?"
  (약 8초) → 인사가 끝난 뒤 청취 창이 열리고 0.3~0.7초 뒤 2.3~2.5초짜리 소리(rms 0.09) →
  whisper 'boom.'/'고맙습니다.', 창 안에서 소리 모델(openWakeWord)이 호출어를 감지해 '비카야'로
  구제, Realtime 은 두 번 다 '오 분'. 미션은 wait 를 두 번 다 무시했다(안내 중이 아님 —
  `intent=wait … -> state=awaiting_user/idle`, 발화 없음). 즉 **이번엔 아무 일도 안 일어났다**.
  - 해석 ①(Realtime 이 틀림): 사용자가 "비카야"를 다시 불렀다. 근거 = 소리 모델이 두 번 다
    호출어를 감지, 사용자 기억("아마 그랬을듯"), Realtime 의 '오 분'이 1분 전 이력(#7 '그래 오분')과
    같음(1회차 결함 때 본 '이력 베끼기' 패턴).
  - 해석 ②(whisper 가 틀림): 사용자가 "오 분"을 다시 말했다. 근거 = 'boom.'은 "오 분"과
    소리가 비슷, 소리 모델은 창 안 짧은 답에도 반짝 오발동한 전력(09-11 실기 10회), whisper 가
    같은 날 "응"→'아멘.', "네"→'반시간.'으로 적은 것과 같은 유형.
  - 결론: **녹음 없이는 못 가린다.** 기록기가 이제 클립을 wav 로 저장한다(scratchpad `clips/`).
    다음 회차에 "인사 끝난 뒤 비카야" 와 "인사 끝난 뒤 오 분"을 각각 재현해 판정한다.
  - 해석 ①이 맞다면 필요한 방어: set_intent 의 confidence 를 로그·관문에 쓰기(지금은 `[RT]` 줄에
    안 찍힌다), heard 가 직전 사용자 발화와 같고 클립이 짧으면 재확인, 소리 모델이 창 안에서
    호출어를 잡으면 Realtime 결과 폐기, whisper 교차검증(지연 1.4 s 되돌아옴).
- **(C) 공통 규칙: 부정어가 섞이면 deny.** 9/2 의 fail-closed("네. 아니. 아니.") 규칙이
  "아니 테스트3로 가자" 같은 **정정 발화**를 취소로 만든다(#19 양쪽). 부정어 + 목적지명이
  함께 있으면 새 목적지 재확인으로 바꿔야 한다.
- (D) Realtime 숫자 오청취 1건(#18). 표본이 적어 경향은 미확정.

  안내 로봇에겐 기각보다 위험하다. 어느 쪽이든 23건 표본으로는 채택 근거가 안 된다.

  같은 대본으로 2회차. ③ 그때 Realtime 이 앞서면 채택, 아니면 whisper + (A)(C) 로 간다.
- 사용자 확인 결과(실기 직후): #3 "응", #21 "네" 확정. #11·#12 는 "아마 비카야" → 재질문에

  긴급어 감지기가 다른 소리에 발동했고 로컬 whisper 가 '감사합니다.'로 걸러 기각한 것이
  맞다(정상 방어). Realtime 과 무관.
