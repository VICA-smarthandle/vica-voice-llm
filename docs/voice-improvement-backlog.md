# VICA 음성·LLM 개선 과제

기록 기준일: 2026-07-26. 실기에서 STT → LLM → Mission → Nav2 주행 종단이 처음 성공한
뒤 발견한 문제와 개선안이다. 우선순위는 안전 > 인식 성공률 > 대화 품질 순으로 둔다.

각 항목의 `근거`는 현재 코드에서 확인한 사실이고, `제안`은 아직 구현하지 않은
`[TARGET]`이다.

## 요약

| # | 문제 | 성격 | 우선순위 |
| --- | --- | --- | --- |
| 5 | "멈춰"를 외쳤는데 멈추지 않음 (1회) | 안전 | 최우선 |
| 2 | 로봇 자기 목소리가 STT에 녹음됨 | 인식 | 높음 |
| 1 | TTS 발화 순서가 꼬임 | 대화·신뢰성 | 높음(근거 수집 먼저) |
| 3 | 엔터 push-to-talk → wakeword 전환 | 사용성 | 중간 |
| 4 | TTS 답변이 정형적 | 대화 품질 | 중간 |

2·3·5는 모두 **마이크 입력 경로**를 공유한다. 따로 고치지 말고 입력 파이프라인을 한
번에 재설계하는 편이 낫다.

## 5. "멈춰"를 외쳤는데 멈추지 않음 (1회)

가장 먼저 다룬다. 안전 경로이기 때문이다.

### 관찰

주행 중 "멈춰"를 외쳤으나 정지하지 않은 사례가 1회 있었다. 현장 판단은 "긴급어를
못 알아들었다"였고, wakeword 학습으로 해결하려 했다.

### 근거

`src/emergency_monitor.py`를 보면 인식 실패 말고도 **구조적으로 못 듣는 구간**이 있다.

| 요소 | 기본값 | 영향 |
| --- | --- | --- |
| TTS 재생 중 mute | `/vica/tts_state` 구독 | 로봇이 말하는 동안 감시 정지 |
| mute 해제 후 보류 | `_resume_at = now + window_sec` (2.0초) | **발화 종료 후 2초 추가 사각지대** |
| `cooldown_sec` | 2.0초 | 직전 이벤트 후 2초 무시 |
| `rms_threshold` | 0.01 | 음량이 낮으면 STT 자체를 생략 |
| `window_sec` / `hop_sec` | 2.0 / 0.5초 | 짧은 "멈춰"가 창 경계에 걸리면 잘림 |
| 모델 | `small` (`VICA_EMERGENCY_STT_MODEL`) | medium 대비 인식률 낮음 |

즉 로봇이 안내를 말하는 중이거나 **말이 끝난 직후 약 2초 동안은 긴급어를 아예 듣지
않는다.** 주행 중에는 안내 발화가 잦으므로 이 구간에 겹칠 확률이 낮지 않다.

사각지대는 자가 트리거(스피커로 나간 자기 목소리를 긴급어로 오인)를 막기 위한 것이라
그 자체는 근거 있는 설계다. 문제는 **대체 수단 없이 감시를 완전히 끈다**는 점이다.

### 제안 `[TARGET]`

1. **원인 먼저 확정한다.** 같은 상황을 재현해 `emergency_monitor`에 판정 로그를 남긴다.
   현재는 감지했을 때만 로그가 남아, 못 들었는지·mute였는지·게이트에 걸렸는지 구분할 수
   없다. 최소한 다음을 남긴다: 창별 RMS, mute 여부, STT 결과, 판정 결과.
2. **하드웨어 AEC를 검토한다.** 마이크가 reSpeaker USB 4-Mic Array **v3.0**(XVF3000,
   2886:0018)이므로 에코 제거·빔포밍을
   쓰면 로봇 발화 중에도 감시를 유지할 수 있다. mute 자체를 없애는 것이 근본 해결이다.
3. **whisper 대신 전용 키워드 스포터를 쓴다.** 긴급어는 어휘가 6개로 고정이다
   (`멈춰`, `정지`, `스탑`, `스톱`, `안돼`, `위험해`). openWakeWord 류의 KWS는 whisper보다
   지연이 짧고 무음 환각이 없어 상시 감시에 적합하다. 3번 과제와 같은 작업이다.
4. **사각지대를 줄인다.** AEC 도입 전까지는 `_resume_at` 보류를 창 길이 전체가 아니라
   실제 잔향 길이만큼으로 줄이는 것을 검토한다. 단, 자가 트리거 시험
   (`docs/voice-field-test.md` 2-1)을 반드시 다시 통과해야 한다.
5. **물리 E-stop이 1차 수단임을 운영 문서에 유지한다.** 음성 긴급어는 보조 수단이다.

## 2. 로봇 자기 목소리가 STT에 녹음됨

### 관찰

엔터로 녹음을 시작한 뒤 로봇이 말하면, 그 소리가 그대로 마이크로 들어가 인식된다.

### 근거

`src/ros_stt_node.py`는 `/vica/tts_state`를 **구독하지 않는다.** 발행만 두 개
(`/vica/user_text`, `/vica/tts_request`) 있고 구독은 없다. 반면
`src/ros_emergency_node.py`는 `/vica/tts_state`를 구독해 감시를 mute한다.

즉 자가 트리거 방어가 긴급어 감시에만 있고 **대화 STT에는 없다.**

`src/stt.py`의 `record_until_enter()`도 엔터를 누를 때까지 무조건 녹음하므로, 그 사이
재생된 로봇 음성이 전부 담긴다.

### 제안 `[TARGET]`

1. `ros_stt_node`가 `/vica/tts_state`를 구독한다.
2. 정책을 정한다. 셋 중 하나를 골라야 하며 사용자 경험이 달라진다.
   - **차단**: TTS 재생 중에는 녹음을 시작하지 않는다(가장 단순, barge-in 불가)
   - **분할**: 재생 구간의 오디오를 버리고 나머지만 인식한다
   - **barge-in 허용**: AEC로 자기 목소리를 제거하고, 사용자가 끼어들면 TTS를 중단한다
     (가장 자연스럽지만 AEC 필요 — 5번 과제와 공유)
3. `docs/voice-field-test.md`의 "로봇이 말하는 중 끼어들기" 항목이 이 결정에 달려 있다.

## 1. TTS 발화 순서가 꼬임

### 관찰

명령 순서가 꼬이는 경우가 있고, 한 번 꼬이면 엉뚱한 목적지로 가거나 엉뚱한 답을 한다.
**재현 근거가 아직 부족하다.** 다음 발생 시 STT·TTS 터미널 로그와 영상을 함께 남긴다.

### 근거 (현재 코드에서 확인한 것)

`src/tts_queue.py`의 큐는 **발생 순서 보존이 아니라 우선순위·신선도 정책**이다. 다음
동작이 "순서가 꼬였다"로 보일 수 있다.

| 동작 | 코드 | 결과 |
| --- | --- | --- |
| 우선순위 재정렬 | `_sort()`가 `(priority, seq)`로 정렬 | 나중에 온 `response`가 대기 중 `narration`을 추월 |
| 중복 억제 | `push()`가 2초 내 같은 문장을 거절 | 같은 안내를 두 번 요청하면 두 번째가 **조용히 사라짐** |
| 정원 초과 폐기 | `_trim()` (`max_len=8`) | 낮은 우선순위 오래된 항목부터 **조용히 삭제** |
| 긴급 선점 | `EMERGENCY` push 시 비긴급 전부 제거 | 대기 중 안내가 모두 사라짐 |

여기에 지연이 겹친다. LLM 응답이 2~3초, TTS 합성이 1~2초 걸리므로 사용자가 말한 순서와
로봇이 말하는 순서가 어긋나 보이기 쉽다.

또한 **거절·폐기가 로그에 남지 않는다.** `PushResult.reason`을 만들어 두고도 노드가
기록하지 않아, 사후에 "왜 그 말이 안 나왔는지" 추적할 수 없다.

### 제안 `[TARGET]`

1. **로그부터 보강한다** (다음 재현 전에 반드시).
   - `push` 거절 사유(`중복`, `빈 문자열`)와 `_trim` 폐기를 WARN으로 남긴다
   - 재생 로그에 `seq`와 대기 시간을 포함한다
   - `/vica/user_text` → `/vica/intent` → `/vica/tts_request`를 잇는 **턴 ID**를 붙인다
2. **턴 경계를 도입한다.** 새 발화가 접수되면 이전 턴의 `response`는 폐기한다. 지금은
   이전 질문의 늦은 답이 새 질문의 답보다 먼저 나갈 수 있다.
3. **주행 확정 안내는 순서를 보장한다.** Mission Manager의 `MSG_START`처럼 상태와 결합된
   문구는 추월·폐기 대상에서 제외하는 것을 검토한다.
4. 재현 자료를 모은 뒤 위 가설(추월·중복억제·폐기 중 무엇인지)을 확정하고 고친다.

## 3. 엔터 push-to-talk → wakeword 전환

### 관찰

현재는 터미널에서 엔터를 눌러야 녹음이 시작된다. 시각장애인 사용자에게는 쓸 수 없는
방식이고, 개발 편의용 임시 구조다.

### 근거

`src/ros_stt_node.py`가 `input()` 루프로 동작한다. `docs/voice-field-test.md`도 "말로
대화 시작"을 "마이크 장치 충돌 때문에 구조 변경 필요"로 기록한다.

다만 실측 결과 **PulseAudio 경유로 두 스트림 동시 열기는 정상 동작한다**(2026-07-26
확인, 각각 같은 오디오 수신). 따라서 장치 충돌보다는 **입력 파이프라인이 두 곳에 나뉘어
있는 구조**가 실제 제약이다.

### 제안 `[TARGET]`

1. **마이크 스트림을 하나로 합친다.** 현재 `emergency_monitor`와 `stt`가 각각
   `sd.InputStream`을 연다. 단일 오디오 서비스가 창을 만들어 긴급어 감시·wakeword·대화
   STT에 나눠 주는 구조가 낫다. 2·5번 과제의 전제이기도 하다.
2. **wakeword 모델을 확보한다.** openWakeWord 한국어 커스텀 모델을 학습하고, 긴급어
   6개도 같은 KWS로 처리한다(5번 제안 3과 동일 작업).
3. **발화 종료 판정을 VAD로 바꾼다.** 엔터 대신 무음 지속으로 녹음을 끝낸다. 이때
   앞뒤 무음이 줄어 STT 정확도도 함께 오른다.
4. 전환 후에도 **엔터 방식을 개발용으로 남긴다.** 조용한 환경 재현 시험에 필요하다.

## 4. TTS 답변이 정형적

### 관찰

답변이 딱딱하고 반복적이다. 현장 인상은 "LLM이 만드는 게 아니라 미리 만든 문구"였다.

### 근거

절반만 맞다. 실제로는 두 주체가 나눠 말한다.

| 상황 | 말하는 주체 | 문구 |
| --- | --- | --- |
| 질문·확인·명확화 | LLM | `intent.reply` (매번 생성) |
| **주행 확정 안내** | Mission Manager | `MSG_START` 등 **고정** |
| 접수 신호·재시도·실패 | 음성 노드 | `src/replies.py` **고정** |

`src/tts_queue.py`의 `request_for_intent()`는 `navigate + need_confirm=False`일 때 LLM을
침묵시킨다. Mission gate를 통과해야 결과를 알 수 있는데 LLM이 먼저 "안내하겠습니다"라고
말하면 거절 시 사용자가 오해하기 때문이다. 이 설계는 유지해야 한다.

딱딱하게 느껴지는 부분은 대부분 **고정 문구 쪽**이다.

### 제안 `[TARGET]`

1. **목적지별 문구를 먼저 활용한다.** `destinations.yaml`에 이미 `confirm_prompt`,
   `arrival_message` 필드가 있다. 지금은 대부분 비어 있어 기본 문구로 대체되고 있다.
   목적지마다 자연스러운 문장을 채우면 코드 변경 없이 개선된다. **가장 비용이 낮다.**
2. **고정 문구에 변형을 준다.** 같은 의미의 문장 2~3개를 두고 번갈아 쓴다. 단
   `src/replies.py`의 주석대로 모든 문구는 자가 트리거 검사(`tests/test_spoken_text.py`)를
   통과해야 하므로, 변형도 같은 검사를 거친다.
3. **안전·상태 문구는 고정을 유지한다.** E-stop, 거절 사유, 도착 알림은 정확성이
   우선이다. 시각장애인 사용자에게는 예측 가능한 문구가 오히려 도움이 된다.
4. LLM에 말투 가이드를 주되, 목적지 이름과 상태는 반드시 코드가 채운 값을 쓰게 한다.

## 공통: 다음 시험에서 남길 것

1번 문제의 재현 근거를 위해 다음을 함께 기록한다.

- STT 터미널 전체 로그 (발행 시각 포함)
- 음성·LLM launch 터미널 전체 로그 (`vica_llm`, `vica_tts`, `vica_emergency`)
- Mission Manager 터미널 로그 (gate 판정 사유)
- 영상 (발화 시점과 로봇 응답 시점의 시간차 확인용)
- 발화한 문장과 기대한 동작을 시간순으로 적은 메모

로그 시각은 ROS 로그의 epoch 값을 그대로 쓰면 세 터미널을 맞춰볼 수 있다.
