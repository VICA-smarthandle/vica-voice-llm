## 1. 왜

지금 해석기는 "이 말이 어떤 질문의 대답인지"를 모른 채 의도 하나(`_IntentDraft.intent`)만 낸다. 질문별 처리는 여러 곳에
덧대어 있다(`_shortcut_intent` 의 확인 대기, `_mission_question_answer`, `_audio_short_answer`, 미션의 09-01 규칙).
덧대지 않은 자리에서 꼬인 것이 11-18 실기와 기준 점수에 남았다.

- 온라인 실기 13:46: 확인 질문 중 "거기 어디야" → Realtime 이 같은 목적지를 다시 제안 → 미션 09-01 규칙(확인 중 같은 곳
  재제안 = 승낙)으로 **출발**. 사용자: 막는 임시 규칙은 넣지 않는다 — 질문 종류별 해석으로 푼다.
- 13:49:22: "다시 가자"에 Realtime 이 재개를 확정으로 내 **묻지 않고 재출발**.
- 13:51:22: "다시 출발할까요?"에 "아니" → 취소로 읽혀 "안내를 취소할까요?"를 한 번 더 물음.
- 기준 점수(208행, 잘못된 행동): Mi:dm 17 · gpt-5.4-mini 10~12 · Realtime 11~13(3회).
  Realtime 이 한 번이라도 틀린 19행 중 **7행은 통째로 짧은 대답**이다 — "삼십분."을 15분으로(분 3행), "안내가 필요
  없으신가요?"의 "네"·"그래"를 반대로(3행), 본인 확인 질문의 "네. 네."를 목적지로(1행). 받아쓴 글자에 지금 있는 짧은 대답
  규칙(`classify_short_reply`·`parse_wait_minutes`)을 쓰면 7행 모두 정답이다(계산). Mi:dm 17행에는 그런 행이 1개뿐이다.
- 사용자 11-18: LLM 이 지어내는 멘트가 어색하다.

## 2. 11-18 에 바뀐 전제 (사용자 결정)

| 결정 | 이 설계에 주는 것 |
|---|---|
| 외부 API 두 경로의 LLM 출력은 도구 호출(`set_intent` \| `reserve_facility`) — 예약 설계 5.1 | 새 칸은 `set_intent` 의 인자, 곧 `_IntentDraft` 의 칸으로 더한다. 형식을 두 번 고치지 않는다 |
| "로컬은 음성안내만, 외부API만 음성에이전트" | 로컬 midm2-mini 는 지금 구조화 출력 그대로. 같은 `_IntentDraft` 칸을 받는다(안내 중의 대답 해석은 음성 안내다 — 사용자 "추천대로") |
| "LLM을 거치지 않으면 너무 부정확할 때가 많다" | **새 글자 규칙을 만들지 않는다.** 바탕 설계 4.3 c 의 목적지·고르기 글자 규칙은 넣지 않고 LLM 에 둔다 |
| 짧은 대답은 예외(사용자 "추천대로") | 이미 있는 규칙(통째로 네/아니요 · N분)만, 소리 모드에서도 받아쓴 글자에 먼저 쓴다(바탕 설계 D11 유지, 근거 1절의 7행) |
| 지시문 본문은 고치지 않는다(예약 설계 5.1) | 턴마다 바뀌는 정보(열린 질문)는 지시문 끝 `[지금 상황]` 블록에 넣는다 |
| 순서(사용자 "추천대로") | 예약 계획의 도구 출력 작업(글자 경로 · Realtime)이 들어간 뒤 구현을 시작한다 — 같은 파일을 고친다 |

## 3. 목표 · 하지 않는 것 · 실패로 보는 것

- 목표: LLM 이 열린 질문의 종류를 알고 대답 값(`answer`)을 낸다 · 미션이 그 값으로 처리해 1절의 세 장면이 없어진다 ·
  208행의 잘못된 행동이 줄어든다 · LLM 이 지은 문장의 말투를 다듬는다.
- 하지 않는 것: 새 글자 규칙 · 예약 대화(예약 설계) · 로봇에게 한 말인지 판정(`addressed`·`not_for_robot`, 바탕 설계 5단계) ·
  되묻기 3단계와 새 멘트(4단계) · 지시문 본문 고치기 · `.env` 경로 선택(6단계).
- 실패로 보는 것: 기준 점수가 2 넘게 나빠짐(±2 는 흔들림) · 반응이 느려짐(바탕 설계 F1) · 확인 없이 출발 · 한 질문에 두
  목소리 · 예약 흐름이 깨짐(예약 진행 중의 승낙·거절은 예약이 받는다 — 예약 설계 5.3).

## 4. 설계

### 4.1 LLM 출력 칸 — `answer`
- `_IntentDraft` 에 `answer` 한 칸을 더한다: `yes` · `no` · `destination` · `choice` · `minutes` · `other`(질문과 상관없는 명령·질문) ·
  `unclear` · 빈 값(열린 질문 없음). 값은 지금 칸을 그대로 쓴다 — 목적지·고른 곳은 `destination_candidate`, 분은 `wait_minutes`.
- 세 경로가 같은 칸을 받는다: 로컬은 구조화 출력의 칸, 외부 API 두 경로는 `set_intent` 인자(Realtime 은
  `realtime_intent.py` 의 손으로 적은 인자 목록에도 더한다).
- 로컬은 질문 종류마다 `answer` 의 허용 값만 남긴 스키마를 쓴다(바탕 설계 4.3 d — 구조화 출력이라 강제된다). 외부 API 는
  허용 밖의 값이 오면 코드가 `unclear` 로 바꾼다.
- `intent` 칸은 지금처럼 채운다. `answer` 가 생겨도 옛 처리 길이 그대로 돈다.
- `repeat`("비카야"만)은 LLM 이 아니라 지금의 호출어 지름길이 낸다. `not_for_robot` 은 이번에 쓰지 않는다.

### 4.2 열린 질문을 LLM 에 알린다
- 음성 노드가 쥔 질문 기록(`self._question`, `/vica/question`)으로 `[지금 상황]` 에 한 줄을 넣는다.
  예: `- 로봇이 물은 질문: "사회복지로 안내해드릴까요?" (확인 질문 — answer 는 yes·no·destination·other·unclear 중 하나)`
- 지금의 시간 기준 표시("방금 질문하고 답을 기다리는 중", `_followup_until`)와 `mission_question.ASK_FRESH_SEC = 40.0` 은 질문
  기록으로 바꾼다 — 질문이 열려 있는 동안만 참이다(바탕 설계 7절 3-나).
- 질문이 없으면 줄이 없고 `answer` 는 빈 값이다.

### 4.3 해석 순서 (글자·소리 공통)
1. 긴급어·멈춤 말 — 지금 그대로.
2. 예약 진행 상태 — 예약 설계 5.3 이 정한 대로(이 설계 밖).
3. 짧은 대답 규칙 — **이미 있는 것만**: 통째로 네/아니요(`handle_mode` 낱말), N분(`parse_wait_minutes`), "비카야"만(호출어 지름길),
   3-나-1 의 일시정지·재개 낱말. 열린 질문의 종류에 맞을 때만 `answer` 를 채운다(네/아니요 = `confirm`·`yesno`·
   `yesno_inverted`, 분 = `minutes`).
   - 소리 모드: 받아쓴 글자가 통째로 이 꼴이면 Realtime 결과 대신 이 대답을 쓰고, Realtime 결과는 로그에만 남긴다.
   - "안내가 필요 없으신가요?"(`yesno_inverted`): 규칙은 들은 대로 `yes`/`no` 만 낸다. 뜻(네 = 필요 없음)은 미션이 질문 종류로 읽는다.
4. LLM — 그 밖의 모든 말. 4.1·4.2 로 `answer` 를 함께 낸다.

### 4.4 음성 → 미션
- `VicaIntent` 끝에 `question_id`(읽을 때 열려 있던 질문) · `answer` · `answer_value`(목적지 id · 분)를 더한다(바탕 설계 4.2,
  `speaker_*`·`ask_*` 와 같은 방식 — 옛 소비자와 호환).
- 음성이 쥐고 있던 "다시 출발할까요?" 판단(`schema.should_forward_intent`, 보류·다시 묻기)을 없애고 재개 제안을 미션에 보낸다(4.5).

### 4.5 미션 — `question_id` 가 지금 열린 질문과 같을 때 `answer` 로 처리
- 확인 질문(`confirm`): `yes` → 출발 · `no` → 접기 · `destination`(다른 곳) → 그곳으로 다시 확인(바탕 설계 C3) · `other` → 질문을
  두고 그 의도대로(사용자 질문이면 음성이 답하고 미션이 질문을 한 번 다시 들려준다 — 11-18 오프라인 13:12 동작) · `unclear` →
  지금의 다시 묻기. **`answer` 가 온 발화에는 09-01 규칙(같은 곳 재제안 = 승낙)을 쓰지 않는다.**
- 재개: 미션이 재개 요청을 받으면 스스로 "다시 출발할까요?"(`yesno`)를 묻는다(바탕 설계 C8). 그 질문이 열려 있지 않은데
  확정 재개가 오면 묻는 쪽으로 낮춘다(3-가의 '확인 없이 나온 확정은 제안으로'와 같은 원칙). `yes` → 재출발, `no` → 일시정지 유지.
- 그 밖의 질문(`yesno`·`yesno_inverted`·`minutes`·`choice`·`open`)은 `answer` 를 지금의 의도 처리와 같은 결과로 잇는다. 칸마다의
  결과는 계획에서 반응표 시험으로 못 박는다.
- `question_id` 가 다르거나 빈 값이면 지금처럼 `intent` 로 처리한다(늦은 대답의 되묻기는 4단계).

### 4.6 말투 다듬기 (바탕 설계 4.6)
- LLM 이 지은 문장(`ask_text`, 사용자 질문의 답)이 TTS 로 가기 전에: 끝맺음 고치기("~시는지요?" → "~시나요?" 등, 조사 130건의
  어색한 문장에서 시작) → 못 고치는 깨진 문장(한국어 아닌 글자, 길이 상한 초과)만 정해진 문장으로 바꾼다. 고친 것은
  "고치기 전 → 고친 뒤"로 로그에 남긴다.
- 정해진 질문은 이미 고정 문장이다(확인 질문 = 미션 `confirm_prompt`, "다시 출발할까요?" = `RESUME_CONFIRM`).
- 이것은 해석이 아니라 내보내는 문장을 고치는 일이라 2절의 "새 글자 규칙을 만들지 않는다"에 걸리지 않는다고 본다(P3).

## 5. 단계와 확인

| 단계 | 내용 | 확인 |
|---|---|---|
| 1 측정만 | 4.1·4.2·4.3 + 재생 도구가 `answer` 로 채점. 미션으로 나가는 것은 지금과 같다 | 208행: 기준(Mi:dm 17 · gpt 10~12 · Realtime 11~13)보다 2 넘게 나빠지지 않는다. 목표는 감소 — Realtime 의 짧은 대답 7행. 지연 p50·p90 도 같이 본다 |
| 2 동작 | 4.4·4.5 — `vica_interfaces`·미션 빌드 | 반응표 시험 · 실기: 온라인 확인 중 "거기 어디야"(출발하지 않음) · "다시 가자"(항상 묻는다) · "다시 출발할까요?"에 "아니" · 오프라인 3-나-1 네 장면 그대로 |
| 3 말투 | 4.6 | 조사 130건 문장에 돌려 고친 결과를 사용자가 훑어봄 · 실기에서 어색한 문장 수집 |

- 1단계 결과가 기준보다 나쁘면 2단계로 가지 않고 사용자에게 보고한다.
- 구현은 예약 계획의 글자 경로·Realtime 도구 출력 작업 뒤에 시작한다. 계획서는 그 코드가 들어간 뒤의 모양을 기준으로 쓴다.

## 6. 빌더에게 맡기는 것

- `[지금 상황]` 질문 줄의 문구, 로컬 스키마를 질문 종류별로 좁히는 구현, 소리 모드에서 받아쓴 글자와 Realtime 결과가 같은
  발화를 한 번만 처리하게 하는 자리(지금의 이중 처리 막기와 같은 곳).
- 미션의 `answer` → 동작 표의 세부(반응표 시험으로 못 박는다).
- 말투 끝맺음 규칙 목록과 길이 상한(조사 자료로 정한다).

## 7. 사용자 확인

- 11-18 에 답을 받은 것: 짧은 대답 규칙은 소리 모드에도 · 로컬에도 넣는다 · 순서는 예약의 도구 출력 뒤.
- 내 판단(다르게 정하시면 고친다)
  - P1 `answer` 값에서 `repeat`·`not_for_robot` 은 이번에 뺀다(앞의 것은 지금 지름길이 하고, 뒤의 것은 5단계).
  - P2 "다시 출발할까요?"에 "아니" → 미션이 **"알겠습니다. 다시 출발하려면 말씀해 주세요."**(11-18 정하신 `MSG_PAUSE_KEPT`)를
    말한다. 지금은 음성이 "알겠습니다. 계속 진행할게요."라고 한다 — 멈춘 채 두는 장면에 맞지 않는다.
  - P3 말투 다듬기의 끝맺음 고치기는 넣는다(4.6).
