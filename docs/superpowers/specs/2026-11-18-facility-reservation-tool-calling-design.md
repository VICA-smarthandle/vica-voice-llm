## 4. 방식 비교

| | 가. 칸만 늘리기 | 나. LLM 이 도구를 부르고 대화도 이끎 | 다. LLM 은 도구만 부름(선택) |
|---|---|---|---|
| 방식 | `reserve` 의도와 시설·날짜·시각·이름 칸을 `_IntentDraft` 에 추가 | 도구를 주고 이름 묻기·되읽기·완료 문장도 LLM 이 지음 | 값은 LLM 이 도구 인자로 읽고, 묻는 문장·확인·저장은 코드와 미션 |
| 도구 호출인가 | 아님 | 맞음 | 맞음 |
| 되읽은 내용 = 저장 내용 | 보장 | 보장 안 됨 | 보장 |
| 도구 추가 | 칸이 계속 늘어남 | 도구만 추가 | 도구만 추가 |

'다'를 고른 근거(11-18 측정, 같은 발화 32개, 도구 3개 중 하나를 항상 부르게 한 조건):

| 모델 | 예약 12: 값까지 맞음 | 그 밖 13 | 이름 대답 2 | 전체 32 | 평균 응답 |
|---|---|---|---|---|---|
| gpt-5.4-mini | 12 | 13 | 2 | 32 | 1.0 s |
| Realtime(글자 입력) | 12 | 12 | 2 | 31 | 0.9 s |
| 로컬 midm2-mini | 3(말하지 않은 값을 버리면 12) | 9 | 0 | 16 | 1.6 s |

- 외부 API 두 모델은 값 읽기와 이름 대답을 맡겨도 맞았다. 그래서 해석은 LLM 에 두고 코드는 검사·계산·저장만 한다(D12).
- 로컬은 말하지 않은 값을 지어내고, 이름 대답에 도구를 다시 부르지 않고 완료를 말했다. 로컬에는 도구를 주지 않는다(D11).
- 업무 도구만 주고 고르게 두면 외부 API 모델은 그 밖의 말에 글로 답한다("화장실로 안내할게요."). 의도 값이 아니어서 그대로
  못 쓴다. 그래서 모든 말을 도구 호출로 받는다(5.1).
- Realtime 은 64번 가운데 시각을 한 번 틀렸다("오후 네 시" → 14:00). 되읽기 확인(②)에서 사용자가 잡는다.
- 한계: 측정용 짧은 지시문, 지은 문장, 한 번씩, Realtime 은 글자 입력. 이름 대답은 앞선 도구 호출 기록을 넣어 준 조건이었다.
  운영 조건은 7절에서 다시 잰다.

## 5. 구조

```
받아쓴 글자·소리
  → 긴급어·멈춤 말(지금 그대로, LLM 이전)
  → 글자 규칙(지금 그대로)
  → LLM: 도구 하나 호출 — set_intent | reserve_facility      ← 출력 형식이 바뀜(5.1)
       진행 중인 예약이 있으면 [지금 상황]에 한 줄(5.3)
       reserve_facility → 예약 진행 상태(5.2)
       set_intent       → 예약 진행 중의 승낙·거절은 예약이 받는다(5.3). 그 밖은 지금의 VicaIntent 흐름
  → VicaIntent(ask_text·ask_kind) → 미션이 말함(지금 그대로)
예약 저장 → 예약 파일(5.4) → /vica/reservation/event → 앱 팝업·목록(5.5)
```

### 5.1 LLM 출력: 모든 말을 도구 호출로 (외부 API 두 경로)

- 도구 두 개.
  - `set_intent`: 인자는 지금 `_IntentDraft` 의 칸 그대로(Realtime 은 지금처럼 `heard_text` 포함). 예약이 아닌 모든 말.
  - `reserve_facility`: `facility`(시설 목록의 이름) · `date`(사용자가 말한 표현 그대로) · `start_time`·`end_time`(24시간 HH:MM,
    `end_time` 은 끝 시각이나 쓰는 시간을 말했을 때만) · `name`(말했을 때만). 필수 인자는 없다. Realtime 에서는 `set_intent`
    처럼 `heard_text`(들린 말 그대로)를 함께 받는다.
- 언제 부르는지는 도구 설명에 적는다: 시설을 예약해 달라는 말, 그 시간에 쓸 수 있냐는 말, 진행 중인 예약에 대한 대답(이름·날짜·
  시각·시설)에 호출한다. 사용자가 이번에 말한 값만 넣는다. 어디로 가자는 말은 이동이므로 `set_intent` 다. 실제 예약은 사용자
  확인 뒤 시스템이 한다.
- 지시문(`_build_system_prompt`·`build_audio_prompt`)은 고치지 않는다. 지시문은 로컬 폴백도 같이 쓰므로, 거기에 "도구를
  호출한다"를 넣으면 도구가 없는 로컬의 해석이 흔들린다.
- 저장(commit)은 도구로 주지 않는다. LLM 이 부를 수 있는 것은 예약 '요청'까지다.
- 경로별 구현
  - gpt-5.4-mini: `ChatOpenAI.bind_tools([...], tool_choice="required")`. 측정에 쓴 방식(`measure_cloud.py`).
  - Realtime: 세션 `tools` 에 두 도구, `tool_choice` 를 `set_intent` 강제에서 `"required"` 로.
  - 로컬 midm2-mini: 바꾸지 않는다. 지금의 구조화 출력 그대로다(D11).
- 도구 호출이 없거나, 목록에 없는 도구 이름이거나, 인자가 맞지 않으면 지금의 실패 처리(`LLM_UNAVAILABLE` 갈래)와 같은 길로 보낸다.
- 두 경로를 각각 `.env` 로 끄고 켠다(기본 꺼짐). 꺼진 경로는 지금 코드 그대로 돈다.
- 도구가 없는 경로(스위치 꺼짐·로컬 폴백)로 예약 낱말이 든 말이 오면 문장 ⑨를 말한다.

### 5.2 `reserve_facility` 를 받았을 때 (코드)

아래에서 '글자'는 글자 경로에서는 받아쓴 글자, Realtime 에서는 `heard_text` 다.

1. 시작 조건(P2): 진행 중인 예약이 없을 때는, 미션이 쉬는 상태이고 열린 질문이 없거나 kind `open` 인 질문("네?", "어디로
   가고 싶으신가요?", ③)일 때만 받는다. 그 밖(안내 주행 · 일시정지 · `confirm`·`yesno`·`choice`·`minutes` 질문이 열림)은 ⑨, 끝.
   순찰 중과 사람 접근 질문 중(`awaiting_user`)에는 아무 말도 하지 않는다 — 미션이 넘겨받은 문장을 버리는 상태다.
2. 값은 LLM 이 준 것을 쓴다. 코드는 지어낸 값만 거른다.
   - `name`: 글자에 그 이름이 없으면 버린다.
   - `facility`: 글자에 그 시설의 이름이나 별칭이 없으면 버린다.
   - `date`·`start_time`: 글자에 날짜 낱말·시각 낱말이 하나도 없으면 버린다.
   - `end_time`: 글자에 "까지"나 쓰는 시간 표현("시간", "동안")이 없으면 버린다.
   - `date` 는 LLM 이 준 표현(내일 · 다음 주 월요일 · 11월 20일 · 2026-11-20)을 코드가 날짜로 계산한다. 못 바꾸면 버린다.
   - 시각이 `HH:MM` 꼴이 아니면 버린다.
   - 진행 중인 예약이 있으면 새로 온 값만 덮고 나머지는 쥔 값을 쓴다.
3. 모자란 값을 차례로 묻는다: 시설 → ⑦, 날짜나 시각 → ⑤.
4. 끝 시각 = `end_time`, 없으면 시작 + 시설의 기본 시간(D3). 끝이 시작보다 이르거나, 지난 시각이거나, 운영 시간을 벗어나면 ⑧.
5. 같은 시설에 겹치는 예약이 있으면 ④.
6. 이름이 없으면 ①, 있으면 ②(확인 질문).

④·⑧ 뒤에는 시각을 비우고 시설·이름·날짜는 쥔다(날짜가 이미 지난 날이면 날짜도 비운다).

### 5.3 예약 진행 상태 (음성 노드, 한 번에 하나)

- 쥐는 것: 시설 · 날짜 · 시작 · 끝 · 이름 · 넘긴 질문 문장.
- 진행 중이면 `[지금 상황]` 블록에 한 줄을 더한다(P10). 상태만 적고 지시는 적지 않는다.
  예: `[진행 중인 예약] 시설 세미나실 · 날짜 내일 · 시작 14:00 · 끝 16:00 · 이름 (아직 없음) · 방금 물은 것: "성함을 말씀해 주세요."`
- 진행 중의 발화도 평소 해석 경로를 그대로 탄다(D12). 글자 모드는 글자 규칙 → LLM, 소리 모드는 Realtime 이다. 그 결과가
  - `reserve_facility` 면 5.2 로 이어 간다.
  - 승낙 의도(`affirm`)이고 확인(②)을 기다리는 중이면 저장(5.4) → 알림(5.5) → ③.
  - 거절·취소 의도(`deny`·`cancel`)면 ⑥을 말하고 진행 상태를 버린다.
  - 다른 명령(이동·잠깐·다시 출발·대기·끝·도움)이면 진행 상태를 버리고 그 의도를 평소대로 처리한다.
  - 그 밖(못 알아들은 말·질문·지금 질문과 맞지 않는 승낙)이면 대답을 못 받은 것이다(D14). 아래 '두 번까지 묻기'로 간다.
    그 의도는 미션에 보내지 않는다 — 보내면 미션이 질문을 닫아 예약이 말없이 끝난다(11-19 독립 검토 I-2).
  - 예약이 받은 승낙·거절은 미션에 보내지 않는다.
- 두 번까지 묻기(D14, 11-19): 한 질문의 대답을 못 받으면 같은 질문을 한 번 다시 넘기고, 또 못 받으면 ⑩을 말하고 진행
  상태를 버린다. 대답을 못 받은 것으로 세는 것은 세 가지다.
  - 위의 '그 밖' 의도.
  - `reserve_facility` 가 왔지만 새로 받은 값이 없음(지어낸 이름이 걸러짐 · 빈 호출).
  - 듣기 창이 빈손으로 닫힘(`/vica/listen_state` 의 `empty…`, 호출 기각 `empty:wake-…` 은 빼고). 미션이 그 질문을 연 뒤의
    것만 센다.
  새 질문으로 넘어가면 횟수는 다시 0 이다. ④·⑧처럼 새 값을 받아 같은 문장이 다시 나가는 것은 세지 않는다.
- 진행 상태를 말없이 버리는 때: "비카야" 재호출 등으로 다른 질문이 열림 · 미션이 쉬는 상태를 떠남(다음 발화나 빈손 종료 때
  시작 조건을 다시 봄) · 넘긴 질문을 미션이 10초 안에 열지 않음 · 넘긴 뒤 60초 동안 아무 일도 없음 · 대화 맥락이 비워짐
  (`_history.begin_turn`). 내 질문이 닫힌 것만으로는 버리지 않는다.
- 확인(②)의 승낙은 미션이 그 질문을 실제로 연 뒤의 것만 저장으로 잇는다(11-19 독립 검토 I-1).
- 대답을 기다리는 문장(①②③④⑤⑦⑧)은 `VicaIntent.ask_text`·`ask_kind` 로 넘겨 미션이 말한다(`one_voice.held_resume_carrier`
  와 같은 꼴: intent `clarify`, `reply` 빈 값). `ask_kind` 는 ② `yesno`, 나머지 `open`. 쉬는 상태에서 이 꼴이 말해지는 것은
  코드로 확인했다(`mission_logic._say_handed_question`).
- 대답을 기다리지 않는 안내(⑥·⑨·⑩)는 음성 노드가 말한다(P8): intent `question`, `reply` 에 문장. 미션은 의도를 받으면 열린
  질문을 닫고(`question_record` 의 `answer`) 따로 말하지 않는다. `one_voice.voice_may_speak` 는 질문이 열린 동안에도
  `question` 의 답을 허용한다.
- 예약 흐름이 만든 의도는 `ros_node._publish_intent` 의 재청취 기각(`is_relisten_noise`)과 로컬 규칙의 대꾸 바꾸기를 거치지
  않게 한다. `reply` 가 빈 `clarify` 는 질문 뒤 문맥 창 안에서 그 기각에 걸려 버려진다(빌더 검토에서 확인).
- 저장에 실패하면(파일 쓰기 오류) ③ 대신 ⑨를 말하고 진행 상태를 버린다. 저장되지 않은 예약을 완료라고 말하지 않는다.

### 5.4 저장

- 폴더 `~/vica_data/reservations/`(`.env` 로 바꿀 수 있게).
  - `facilities.yaml`: 시설마다 이름 · 별칭 · 기본 시간(시간) · 운영 시작·끝 시각. 시연용: 세미나실, 상담실.
  - `reservations.json`: 예약 배열. 한 건 = `id` · `facility` · `date`(YYYY-MM-DD) · `start`·`end`(HH:MM) · `name` ·
    `source`(`voice`) · `created_at`.
- 쓰기는 임시 파일에 쓴 뒤 이름 바꾸기. 쓰기 직전에 파일을 다시 읽어 겹침을 한 번 더 본다. 읽히지 않는 파일은 덮어쓰지 않는다.
- 순수 모듈로 둔다(ROS 없이 시험): 읽기 · 겹침 판정 · 추가 · 취소.

### 5.5 앱 알림 · 목록 · 취소

- 알림: 음성 노드가 `/vica/reservation/event`(`std_msgs/String`, JSON)를 낸다(D7·P1).
  `{"event": "reservation_created" | "reservation_canceled", "id", "facility", "date", "start", "end", "name", "source", "timestamp"}`
- 목록: `VICA_Supervisor/ros2/map_http_server.py` 에 `GET /reservations/list.json` 을 더한다(경비 기록 `/patrol/events.json`
  과 같은 방식, 읽기만). 앱은 화면을 열 때와 알림을 받을 때 다시 받는다.
- 취소: 앱이 `/vica/reservation/cancel_request`(`std_msgs/String`, 예약 id)를 내면 음성 노드가 파일에서 지우고
  `reservation_canceled` 를 낸다(P5). 앱은 그 알림을 받으면 목록에서 뺀다.
- 앱 화면: 보드 60(더보기 › 시설 예약, 날짜별 목록, 방금 등록 표시, ✕ 취소)·61(새 예약 팝업). 11-18 사용자 승인(D9).

## 6. 문장

②만 값이 들어가는 틀이고 나머지는 고정 문장이다. 전부 사용자 확정(D8).

| # | 문장 | 언제 |
|---|---|---|
| ① | 성함을 말씀해 주세요. | 이름이 없음 |
| ② | {이름} 님 이름으로 {날짜} {시작}부터 {끝}까지 {시설} 예약할까요? | 값이 다 참 |
| ③ | 네, 예약이 완료되었습니다. 이제 어디로 갈까요? | 저장 뒤 |
| ④ | 그 시간에는 이미 예약이 있습니다. 다른 시간을 말씀해 주세요. | 겹침 |
| ⑤ | 언제로 예약할까요? | 날짜나 시각이 없음 |
| ⑥ | 예약하지 않았습니다. | 거절·취소 |
| ⑦ | 어디로 예약할까요? | 시설이 없음 |
| ⑧ | 그 시간에는 예약할 수 없습니다. 다른 시간을 말씀해 주세요. | 지난 시각·운영 시간 밖 |
| ⑨ | 지금은 예약을 받을 수 없습니다. | 쉬는 상태가 아님 · 도구가 없는 경로(스위치 꺼짐·로컬) · 저장 실패 |
| ⑩ | 예약이 취소되었습니다. | 같은 질문을 두 번 물어도 대답을 못 받음(D14, 11-19) |

- ②의 날짜·시각은 말로 읽는다: 오늘·내일·모레는 그 말로, 그 밖은 "11월 20일". 시각은 "오후 두 시", "오후 한 시 반". 끝 시각이
  시작과 같은 오전·오후면 끝의 표시는 뺀다("오후 두 시부터 네 시까지").
- 고정 문장은 미리 합성해 둔다(`src/mission_phrases.py` 방식). ②는 그때 합성한다.

## 7. 측정과 켜는 기준

- 경로별로 도구 출력을 켜기 전에 208행 재생(`tools/answer_replay.py`, 11-18 기준: 잘못된 행동 gpt 10~12 · Realtime 11~13)을
  도구 출력으로 다시 잰다. 기준보다 2 넘게 나빠지면 그 경로는 켜지 않는다(11-18: ±2 는 흔들림).
- 예약 묶음(운영 지시문과 `[지금 상황]` 을 붙인 조건, 모두 38개)
  - 첫 요청 15개(11-18 의 12개 + 끝 시각·길이를 말한 3개): 5.2 를 거친 뒤 값까지 모두 맞는다.
  - 그 밖 13개: `reserve_facility` 호출 0.
  - 이어진 대답 10개(진행 중인 예약 한 줄을 붙임): 이름 "김민수"·"이서연입니다."·"제 이름은 박준호예요.", 값 "내일 오후
    세 시"·"세미나실이요.", 확인에 "그래."·"아니요."·"아니 네 시로 해 줘.", 이름 질문에 "아니, 됐어."·"화장실 먼저 가자." —
    모두 기대한 도구·의도가 나온다.
  - 이어진 대답은 11-18 측정에 없던 조건이다(그때는 도구 호출 기록을 넣어 주었다). 여기서 안 되면 `[지금 상황]` 한 줄 대신
    대화 기록에 도구 호출 기록을 넣는 방식으로 바꾼다.
- 순수 로직 시험: 값 거르기 · 날짜 계산 · 겹침 · 진행 상태 · 문장 만들기 · 저장.
- 실기 장면(주행 없음): 대본 그대로 · 이미 예약 있음 · 확인에 "아니" · 이름을 잘못 들었을 때 "아니" · 이름 질문 중
  "화장실로 가자" · 날짜 없이 "세미나실 예약해 줘" · "두 시부터 세 시까지" · 이름 질문에 대답 없이 지나간 뒤 다시 요청 ·
  오프라인(로컬)에서 "세미나실 예약해 줘"(⑨). 글자 모드와 소리 모드에서 각각 한다.
  합격: 앱 목록·팝업이 저장과 같은 내용, 한 질문에 두 목소리 0, 저장 없는 완료 문장 0.
- Realtime 이 소리에서 이름을 얼마나 듣는지는 실기에서 본다(11-18 측정에 없음). 틀려도 ②에서 걸린다.

## 9. 순서 (각 단계 끝에 확인 가능)

1. 저장 · 날짜 계산 · 진행 상태 · 문장 — LLM 없이 시험으로 확인.
2. gpt-5.4-mini 도구 출력 + 재생 측정 → 켬 → 글자 경로로 대본 실기.
3. Realtime 도구 출력 + 재생 측정 → 켬 → 소리 경로로 대본 실기.
4. 앱 화면·알림·취소 + 지도 서버 목록.

## 10. 3-나-2 와의 관계

3-나-2(질문 kind 별 해석, `answer`·`question_id` 칸)는 LLM 출력 형식을 바꾼다. 이 설계가 그 출력을 도구 호출로 바꾸므로,
3-나-2 는 `set_intent` 의 인자에 칸을 더하는 일이 된다. 3-나-2 계획은 이 설계의 5.1 을 전제로 쓴다.

## 11. 빌더에게 맡기는 것

- `.env` 키 이름과 경로별 스위치 모양, 모듈·함수 이름.
- 날짜 표현을 날짜로 바꾸는 범위(7절의 예약 묶음을 통과하는 선).

- 토픽 QoS, 예약 id 모양, 앱 쪽 모델·화면 코드 구조.
